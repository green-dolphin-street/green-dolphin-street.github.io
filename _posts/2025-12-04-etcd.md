### 1. What is etcd?
* **Definition:** An open-source, strongly consistent, distributed key-value store.
* **Data Model:** Stores data in a simple hierarchical key-value format (similar to a file system mostly, but technically a flat binary key space).
* **Core Philosophy:** Prioritizes **Consistency** (CP in the CAP theorem) over Availability. It ensures that if you read data, it is the absolute latest version; it never serves "stale" data.
* **Interface:** Accessed via a gRPC API (JSON/HTTP is also supported).

### 2. Primary Use Cases
* **Kubernetes (The Standard):**
    * Acts as the primary backing store for all cluster data.
    * Stores the state of Pods, Services, Secrets, and ConfigMaps.
    * If etcd is lost, the Kubernetes cluster is effectively destroyed.
* **Service Discovery:**
    * Applications can register themselves in etcd (e.g., `Key: /services/web/ip`, `Value: 10.0.0.1`).
    * Other apps watch these keys to know where to send traffic.
* **Distributed Locking:**
    * Ensures that only one worker process performs a specific task at a time across a cluster to prevent race conditions.
* **Configuration Management:**
    * Stores global settings or feature flags that need to be propagated to hundreds of application instances instantly.

### 3. Consensus Mechanism: The Raft Algorithm
* **The Goal:** To ensure all nodes in the cluster agree on the state of the data, even if some nodes crash or the network is partition.
* **Node Roles:**
    * **Leader:** Handles all client **writes**. There is only one leader at a time. It replicates data to followers.
    * **Follower:** Passively replicates data sent by the leader. Can handle **read** requests (though reads usually go through the leader to ensure strong consistency).
    * **Candidate:** If a follower stops hearing from the leader, it becomes a candidate and requests votes to become the new leader.
* **The Write Process (Step-by-Step):**
    1.  **Request:** A client sends a write request (e.g., `set x=5`) to the Leader.
    2.  **Log Entry:** The Leader appends this entry to its internal log (uncommitted).
    3.  **Replication:** The Leader sends the log entry to all Followers in parallel.
    4.  **Acknowledgement:** Followers write the entry to their disk (WAL) and send an acknowledgement (ACK) back to the Leader.
    5.  **Quorum & Commit:** Once the Leader receives ACKs from a majority (Quorum), it "Commits" the entry effectively saving it.
    6.  **Response:** The Leader tells the client "Success" and instructs Followers to commit the data.
* **Common Practices & Architecture Rules:**
    * **Odd Number of Nodes:** Clusters are always sized in odd numbers (3, 5, 7).
        * *Reason:* To prevent "Split Brain" (a tie in voting).
    * **Quorum Calculation:** The formula is `(N/2) + 1`.
        * **3 Nodes:** Needs 2 to work (Tolerance: 1 failure).
        * **5 Nodes:** Needs 3 to work (Tolerance: 2 failures).
    * **Why not 7 or 9 nodes?** While more nodes increase fault tolerance, they **decrease write performance**. The Leader must wait for more acknowledgments before committing data. 3 or 5 is the industry standard.

### 4. Hardware Requirements
* **Storage (The Most Critical Component):**
    * **Requirement:** NVMe or high-speed SSD.
    * **Metric:** `fsync` latency must be extremely low. Ideally, the 99th percentile of `fsync` duration should be less than **10ms**.
    * **Why:** Raft requires data to be physically persisted to disk before confirming a write. Slow disks cause leader election timeouts and cluster instability.
* **Network:**
    * **Requirement:** Low latency and high bandwidth (1GbE is minimum, 10GbE recommended for large clusters).
    * **Proximity:** Nodes should run in the same region to minimize round-trip time (RTT). Cross-region etcd clusters are generally avoided due to latency.
* **CPU:**
    * **Requirement:** Dedicated CPU cores.
    * **Usage:** Used heavily for handling high request rates (gRPC) and SSL/TLS encryption/decryption.
* **Memory (RAM):**
    * **Requirement:** Sufficient to cache the key-space.
    * **Usage:** etcd keeps the current state of the keys in memory for fast reads. If the database size is 8GB, having 16GB+ RAM is ideal to avoid swapping.
